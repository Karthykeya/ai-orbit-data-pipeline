# AI Orbit Data Ingestion Pipeline — MCP Servers Module

A modular, API-first ingestion pipeline that produces a clean, verified,
relationship-rich dataset of **75 official Model Context Protocol (MCP)
servers**, per the AI Orbit Data Ingestion trial spec.

## Why the MCP module

The spec allowed picking one module. MCP was chosen because it gives the
richest relationship density with the least ambiguity: every MCP server is
built and maintained by exactly one company, for exactly one underlying
platform, so `Company → develops → MCP` and `MCP → integrates_with → Tool`
edges can be derived deterministically and verified against a single
authoritative page per entity — good ground for demonstrating entity
resolution, deduplication, and validation cleanly rather than volume.

## Architecture

```
Discovery → Extraction → Cleaning → Normalization → Deduplication →
Classification → Description Generation (LLM) → Shaping → Relationship
Mapping → Validation → Write outputs
```

Each stage is an independent module in `src/`, composed by `run.py`. Every
stage takes a list of dicts and returns a list of dicts, so stages can be
reordered, unit-tested, or swapped independently.

| File | Responsibility |
|---|---|
| `src/discovery.py` | Source of raw candidate records (see Data Sourcing) |
| `src/extraction.py` | Field extraction + required-field checks, logs and skips incomplete records instead of crashing |
| `src/cleaning.py` | Text sanitization (strip HTML/whitespace) + URL normalization |
| `src/normalization.py` | Vendor-name canonicalization (explicit alias map + fuzzy-match *candidate surfacing*, never silent auto-merge) |
| `src/deduplication.py` | Exact-key dedup on `(slug(name), vendor_domain)`, keeping the most complete record |
| `src/classification.py` | Assigns `entity_type` and finalizes category tags |
| `src/descriptions.py` | LLM description generation (see below) |
| `src/shaping.py` | Maps working records to the project's Common Entity Schema + MCP metadata block |
| `src/relationships.py` | Derives `Company` entities and `develops` / `integrates_with` edges |
| `src/validation.py` | Final schema + URL integrity checks before write |
| `src/schema.py` | Deterministic UUIDv5 id generation, slugify, logo-URL resolution |

Run it:

```bash
python run.py
# -> data/mcp_servers.json, data/companies.json, data/relationships.json
```

## Data sourcing (Discovery/Extraction)

This is an API-first design: `discovery.py` is written so that swapping in
live HTTP calls (GitHub Search API, vendor docs sitemaps, the MCP Registry
API) requires no change anywhere else in the pipeline — it only needs to
keep returning the same record shape.

The sandboxed evaluation environment this was built in has **no outbound
network access at pipeline-run time**, so discovery/extraction was performed
manually, hitting the same authoritative sources a script would:

- Anthropic's own `modelcontextprotocol/servers` repo and `modelcontextprotocol.io/examples` for the 7 reference servers.
- Each vendor's own developer documentation for the ~68 first-party servers (Stripe, Notion, GitHub, Linear, Cloudflare, Slack, Atlassian, HubSpot, Supabase, etc.) — the exact page checked is recorded per record as `source_url`.
- A directory (`docs.langdock.com`) that explicitly only lists servers it has tested against the vendor's own official endpoint, used to cross-check server URLs and auth types, never as a substitute for the vendor's own docs link.

Every record's `url` field points to the **vendor's own documentation**, not
a third-party aggregator, satisfying the "replace third-party links with the
official source" requirement.

## Logo resolution & verification

`logo_url` is generated by `schema.official_logo_url()` from each record's
**verified apex domain** (the same domain backing `url`), via the Clearbit
Logo API (`logo.clearbit.com/{domain}`) — a domain-keyed lookup that serves
the logo published at that company's own site, rather than a stock-icon or
community-curated image. Because the domain itself was checked against an
official source before being stored, the logo is traceable back to the same
verification as the URL.

## Description generation

Per the workflow, descriptions were generated by an LLM (Claude) after
cleaning and verification. `descriptions.generate_via_llm()` in
`src/descriptions.py` is a ready-to-run Anthropic Messages API call (one
sentence per record, batched); it wasn't executed in this network-isolated
environment, so descriptions were instead written by the same LLM
interactively (identical step, different transport) and cached in
`CURATED_DESCRIPTIONS`. Swapping `descriptions.generate()` to call
`generate_via_llm()` is a one-line change once `ANTHROPIC_API_KEY` and
network access are available.

## Entity resolution & deduplication

- **Normalization** uses an explicit alias map for vendor names rather than
  fuzzy matching alone — brand names are too easy to falsely merge
  ("Square" vs. an unrelated future "Square"). `find_fuzzy_candidates()`
  surfaces near-duplicate names for human review but never auto-merges.
- **Deduplication** keys on `slug(name) + vendor_domain` and keeps whichever
  duplicate has more populated fields, so a partially-extracted record never
  silently wins over a complete one.
- **Ids** are deterministic `UUIDv5`s derived from stable natural keys
  (`schema.stable_uuid`), so re-running the pipeline on unchanged source
  data reproduces identical ids — safe for idempotent re-ingestion.

## Relationship mapping

`relationships.py` emits, for every MCP server:

- `Company --develops--> MCP` (the vendor that built it)
- `MCP --integrates_with--> Tool` (the vendor's own platform/API)

75 MCP records → 69 unique companies (some vendors, like Anthropic, publish
multiple reference servers) → 150 relationship edges.

## Error handling / resilience

- `extraction.py` logs and skips (not crashes on) any record missing a
  required field.
- `validation.py` drops records with duplicate ids, missing schema fields,
  or malformed URLs, logging each drop with a reason, and never lets a bad
  record silently reach the output files.
- All stages are pure functions over lists of dicts — a failure in one
  record never aborts processing of the rest of the batch.

## Deliverables in this repo

```
src/                  pipeline stage modules
data/raw/mcp_seed.py  verified source data (Discovery+Extraction output)
data/mcp_servers.json final MCP entity records (Common Entity Schema)
data/companies.json   derived company entities
data/relationships.json  relationship edges
data/AI_Orbit_MCP_Dataset.xlsx  same data, formatted for Google Sheets

build_sheet.py         builds the spreadsheet deliverable from the JSON outputs
```

## Known limitations / next steps

- Only the MCP module was built out for this submission (per "pick any one
  module"); the same pipeline shape generalizes to Tools, Models,
  Repositories, and Companies with a different `discovery.py` source and a
  different `shaping.py` metadata block per the spec's schema table.
- Live network access would let `discovery.py` hit the GitHub API directly
  for repo stars/language/last-updated on any MCP servers that are also
  open-source repos, enriching the `Repositories` category from the same
  source data.
